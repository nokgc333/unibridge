# ADR-0001: データ交換フォーマットにOpenUSDを採用（FBXとの比較）

## Status
Accepted (2026-09-07)

## Context
HoudiniとBlenderの間でシーン・アセットを相互変換するツールを作るにあたり、まずデータ交換フォーマット自体の選定が必要だった。業界で長年使われてきたFBXと、Pixarが開発し急速に業界標準化しつつあるOpenUSD（以下USD）の2つが主な候補だった。

FBXは単一ファイルにジオメトリ・マテリアル・アニメーション・階層構造をフラットに格納する設計であり、DCC間の交換フォーマットとして広く普及している。しかしFBXは「誰かが書き出したファイルを、別の誰かが読み込んで上書きする」という一方向的な交換モデルを前提としており、複数人が同じアセットの異なる側面（モデリング担当・マテリアル担当・リギング担当）を同時に、非破壊で編集・統合する仕組みを持たない。

USDはこれに対し、Layer（レイヤー）とComposition（コンポジション）という概念を核に持つ。1つのUSD Stageは、複数のLayerをSublayer/Reference/Payload等のComposition Arcで重ね合わせた結果として構築される。各Layerは、シーンの特定の側面（例: モデリングのみ、マテリアルのみ）だけを非破壊に記述でき、上位LayerのOpinion（値の主張）が下位Layerを上書きする形で最終的なStageが決定する。これは単なるファイルフォーマットの違いではなく、「大規模な共同制作を前提としたデータアーキテクチャそのものの違い」である。

## Decision
UniBridgeのコアとなるデータ交換フォーマットにOpenUSD（`usd-core`パッケージ経由の`pxr`モジュール）を採用する。FBXはサポートしない。

## Consequences

良い:
- レイヤー・コンポジションという、USD最大の差別化要素を実装レベルで扱うことになり、「USDワークフローの実装経験」を面接で具体的に語れる（元企画書で「差別化効果が最大級」と評価された理由と直結する）。
- Houdini（Solaris/LOPs）・Blender（USD I/O）ともにUSDをネイティブサポートしており、追加のコンバータ実装が不要。
- 業界標準になりつつあるフォーマットを選ぶことで、実務適用可能性を説明しやすい。

悪い:
- USDのコンポジションは学習コストが高く、実装・説明ともにFBXより難度が高い。
- USDエコシステム（usd-core、DCC側のUSD I/O実装）のバージョン差異による挙動の揺れに注意が必要。

## Alternatives Considered
- **FBX**: 広く普及しているが、上記の通り非破壊な協業モデルを持たず、本プロジェクトが証明したい「DCC非依存のデータ交換基盤」としての説得力に欠けるため却下。
- **Alembic (ABC)**: ジオメトリキャッシュの交換には強いが、コンポジションの概念を持たず、階層構造・マテリアル・命名規則を横断した検証というスコープには合わないため却下。
